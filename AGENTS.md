- Hub de gateways (Gatehub) — adapter `PIX_GATEWAY=hub`: as credenciais são `HUB_URL` (padrão `https://hub-de-gateways.vercel.app`), `HUB_API_KEY` (`hub_live_...`, **não** `PIX_GATEWAY_API_KEY`), `HUB_WEBHOOK_SECRET` (`whs_...`) e `HUB_SLUG` (funil do painel). Com `HUB_API_KEY` definida e `PIX_GATEWAY` vazio o hub já é o gateway ativo; `PIX_GATEWAY` explícito sempre vence (rollback para gateway direta). `POST {HUB_URL}/api/v1/charges` (centavos, `method: "pix"`, `customer.document` string, `ip` do comprador, `reference`, `items`, `tracking`, header `Idempotency-Key`) e `GET /api/v1/charges/{id}` — o id do hub é `<gateway>_<idExterno>` (`velani_8f2a1c`), não é o id da gateway de trás. Webhook `{ event: "charge.updated", charge: { id, gateway, status, amount, method, reference } }` com `x-hub-signature` = `sha256=` + HMAC-SHA256 do corpo bruto; exige `HUB_WEBHOOK_SECRET` (sem ele a rota responde 503) e a validade é reconfirmada na API (`src/lib/hub-webhook.ts`). Status do hub: `pending/paid/failed/canceled/refunded/chargeback` — **não existe `expired`**, então `sup-status` devolve `renewable` (via `primaryUnpayable`) e o navegador renova por ele. Doc e riscos em `docs/hub.md`. Nunca versionar credenciais.
- Gateway PIX do funil, trocável só por env na Vercel. `PIX_GATEWAY_API_KEY` ativa o gateway (padrão `vexigate`); `PIX_GATEWAY` = `vexigate` (nativo: amount em reais, `transaction_id`, `copy_paste`/`pix_qrcode`, webhook HMAC obrigatório com segredo) ou `velani` (Velani Pagamentos API v1.0: amount em centavos, header `x-api-key`, resposta `data.pixQrCode`/`data.expiresAt`, webhook `{ event, data, signature }` com HMAC hex de `JSON.stringify(data)`; **criação exige `sk_live_...`**, a `pk_live_...` é só leitura) ou `beehive` (Beehive Pay API v1: `POST https://api.conta.paybeehive.com.br/v1/transactions`, amount em centavos, auth Basic `base64(SECRET_KEY:x)` — **verificado contra a API: Bearer responde 401**, o adapter ainda repete no 401; **criação exige `sk_live_...`**, a `pk_live_...` só serve para tokenização/3DS no front; exige `customer` (name/email/phone/document — `phone` em E.164 `+5511999999999`: o formato do funil com país e sem `+` volta 422 `customer.phone is invalid`, e a transação sem `phone` é aceita), `items` com `tangible`, `metadata` fixo provider/user_email/order_id/checkout_url/shop_url e `ip`; resposta real `id` numérico + status `waiting_payment` + `pix.qrcode`/`pix.expirationDate`, a imagem do QR é gerada pelo cliente; webhook `{ id, type: "transaction", objectId, url, data }` com `data.amount` em centavos e **sem assinatura documentada** → confirmação só via API) ou `generic` (proxy que traduz o pedido). Fallback FreePay DESATIVADO (blocos `FREEPAY:` comentados nas rotas sup-*). Contrato/adapters em `src/lib/pay-gateway.ts`. Chaves só server-side; never hardcode or expose them.
- The SuperSim funnel ships as static pages under `public/inicio` (`/` redirects there); its payment APIs are the `/api/public/sup-pix`, `sup-status`, `sup-track`, `sup-utmify`, `sup-webhook` server routes; prices and products live only in `src/lib/sup-products.ts` (imported by sup-pix and sup-utmify).
- Envio de vendas para a UTMify (server-side only, contrato em `src/lib/utmify.ts`): `POST https://api.utmify.com.br/api-credentials/orders` com header `x-api-token: {UTMIFY_API_TOKEN}` (opcionais `UTMIFY_PLATFORM`, padrão `SuperSim`, e `UTMIFY_ORDERS_URL`). `sup-pix` envia `waiting_payment` na criação do PIX (dados completos: cliente, produto/valor do catálogo, UTMs, IP) e devolve `createdAt` (UTC 0) na resposta; o navegador (`checkout-shared.js` → `_pixFirePurchase`) chama `/api/public/sup-utmify` quando o pagamento confirma, e essa rota **revalida o pagamento no gateway** (`primaryStatus`) antes de enviar o status `paid` — o navegador nunca decide sozinho que a venda foi paga. O `orderId` na UTMify é o `txnId` do gateway nos dois envios (a UTMify atualiza o pedido em vez de duplicar), e o `createdAt` é sempre o mesmo nas duas chamadas. Sem token configurado, o funil segue normal e só loga o aviso.
- Consulta de CPF da etapa 1 (`public/inicio/2.html`): via proxy server-side `/api/public/sup-cpf?cpf=...` (nunca direto do navegador) — provedor padrão Amnesia Tecnologia, `GET {CPF_BASE_URL}/?token={CPF_API_KEY}&cpf={numeros}`, que responde **sempre HTTP 200**: `{ DADOS: { cpf, nome, nome_mae, data_nascimento, sexo } }` = encontrado (campos vazios = não-encontrado), `{ erro: "..." }` ou texto puro (token vencido) = falha. `CPF_PROVIDER=zipcardx` volta ao provedor antigo (`GET {CPF_BASE_URL}/consult/{numeros}` com `Authorization: Bearer`, 404 = não-encontrado, 429 = excesso). Validação de dígito local nos dois casos. Server-side only via `CPF_API_KEY` + `CPF_PROVIDER` + `CPF_BASE_URL` (+ opcional `CPF_LIMITE_POR_MINUTO`); resposta `{ success, encontrado, cpf, nome, mae, nascimento, sexo, confere? }`. `sup-pix` exige CPF com dígito válido (igual a `criar-pagamento.php:49` do outro projeto).
